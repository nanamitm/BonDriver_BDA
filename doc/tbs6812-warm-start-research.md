# 初回BDA選局要求を省く方法の調査

2026-10-30。**初期化済み状態を再利用できる場合、約8.6秒のBDA呼び出しを省けることを試作と実機試験で確認した。**
作業ブランチは`codex/tbs6812-warm-start-research`。本番のDLL・INIは従来構成を維持している。

## 分かったこと

通常終了後に再オープンしたCXD2857ERは、BDAの初回TuneRequest前からS3コア、24MHz設定、TLV並列出力、ロックを維持していた。
そこで、毎回ベンダー選局で初期化し直す代わりに、既知の状態を検証して既存の直接I2C選局へ引き継ぐ方式を試した。

Freiaの周波数設定域0x0c～0x15は、このI2C読み出し経路では選局前後ともすべて0になり、現在周波数の復元には使えなかった。
そのため試作では、正常終了時に復元した既知のIFとTSIDを、デバイス別の状態ファイルへ保存している。

## 試作の処理

1. 通常のBDAグラフ構築と排他取得は残す。WindowsドライバーはDMAとraw I2Cのために引き続き使用する。
2. 初回選局で状態ファイルを読み、デバイス識別子・IF範囲・S3のTSID・形式・サイズ・チェックサムを検証する。
3. 状態ファイルを削除してから引き継ぐ。選局・受信中は有効な状態ファイルを残さない。
4. 実機のロック、アクティブ状態、データピン、TLV出力、チップID、コア、基準クロック、並列配線、保存TSIDとの一致を確認する。
5. 確認できた場合だけAdoptCached→直接選局を使い、初回のE_NOINTERFACEとベンダーTuneRequestを省く。
6. 保存状態がない・壊れている・実機の前提が一致しない場合は、既存の初回ベンダー選局を行う。
7. 正常終了で元のキャリアへ復元し、再ロックを確認した後だけ状態ファイルを一時ファイルから置き換えて公開する。

カード全体のモード切り替え、チップのコールドリセット、共有REFOUTの再設定は追加していない。
状態ファイルは保存IFを使うための手掛かりであり、実機の確認を省くためのものではない。

## 実測結果

SetChannel開始から復帰までの時間。生TLV出力のプローブで測定し、TVTest描画時間は含まない。

| 条件 | Tuner 0 | Tuner 1 |
|---|---:|---:|
| 保存状態なし：ベンダー選局 | 8.881秒 | 8.845秒 |
| 再オープン後の初回4K：保存状態を再利用（各2回） | 1.013～1.024秒 | 1.008～1.018秒 |
| 再オープン後の初回8K：保存状態を再利用（各1回） | 0.704秒 | 0.667秒 |

保存情報が壊れた場合は8.860秒、保存TSIDと実機が違う場合は8.875秒で従来経路へ戻り、目的のチャンネルを受信した。
フォールバック後の正常終了で作った状態を再利用すると、再び約1.021秒で選局できた。

終了時には復元キャリアの再ロック待ちが加わる。今回の例では約0.5～0.9秒だった。
この確認を省くと、すぐ再起動した際にまだ未ロックで、ベンダー経路へ戻る事象があったため追加した。

各試行は [tbs6812-warm-start-research.csv](tbs6812-warm-start-research.csv) に記録した。

## dantto4k・同時使用・復旧

- 同じ共通DLL・INIを読み込む2プロセスが、別々のチューナーで保存状態を再利用した。
- dantto4k経由の初回4Kは約1.008～1.084秒、初回8Kは約0.694秒。最初の変換済みデータは約1.02～1.48秒で到着。
- 両方使用中の3つ目はOpenTuner失敗。固定指定で使用中のスロットを他方へ切り替えない動作も維持した。
- 片方の終了・再オープン中も、もう片方を45秒間受信させた。
- 試験用の生受信プロセスだけを受信開始後に強制終了し、状態ファイルが残らないことを確認。次回は約8.868秒のベンダー経路で受信・正常終了できた。
- 調査後、本番の共通DLLから2プロセスでB070とB0B0を受信・正常終了し、両TSの同期エラー・連番欠落・TEI・未復号パケットは0だった。

強制終了の試験は生受信プローブであり、TVTest/dantto4kを含む全体の異常終了検証を完了したものではない。

## データ品質の留意点

初回8Kの2ファイルは同期エラー・連番欠落・解析不能が0だった。
一部の高速選局直後の生データには同期外れや連番飛びがあり、dantto4kの5つのTSでも2ファイルに連番飛びが各1件あった。
対象の生ファイルは先頭2MiB（8Kの1例は8MiB）、TSは先頭2,256,000バイトを除くと同期・連番エラーが0だった。
したがって、受信継続中の相手側への影響は見られなかったが、切り替わり直後の品質改善は残っている。
本調査ではこの問題の原因を確定していない。

## 本番採用前に残ること

- コールドスタート、OS再起動、スリープ復帰、別ソフトでの操作後の再利用条件と状態ファイル破棄方針を検証する。
- RF周波数を直接読み戻せない制約がある。保存値の鮮度と外部操作の検出を、本番の運用範囲に合わせて詰める。
- キャッシュ保存先・権限・設定不備・I/O失敗時の扱いを整理する。
- 高速経路に入った後の選局失敗・タイムアウトは現状エラー扱い。復元してベンダー経路へ再試行するかを検討する。
- 新経路でのTVTestのライブ表示と長時間録画を確認する。
- 初回のハードウェア初期化自体を直接制御へ移す方法は未実装。初期化済みと確認できない場合は従来方式が必要。

## 試作の再現

対象チューナーを空け、作業ブランチで次を実行する。試験専用の新しいworkフォルダーを作り、本番には配置しない。

```powershell
./tools/build-tbs.ps1
cmd /c tools\test-tbs6812.cmd
cmd /c tools\build-probe.cmd work\bon-driver-probe-dual.exe
./tools/research-warm-start.ps1
```

試作を使うINIは、検証フォルダーで次の設定を追加したもの。既定は無効。

```ini
[TBS6812]
ExperimentalWarmStart=1
WarmStartCacheDirectory=F:\path\to\isolated-test\cache
InspectWarmState=1
```

実施した試験の生ログ・キャプチャは`work/warm-validation-20261030-213212/`。
`dantto-test.log`が同時使用試験、`raw/TBS6812.log`が状態検証とフォールバック、`stock-check.log`が本番DLLでの確認。

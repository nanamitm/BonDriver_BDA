# TBS6812 ISDB-S3 初回選局の計測

2026-10-30、空いているTBS6812のTuner 0/1をそれぞれ3回開き直して計測した。
計測用ビルドは作業フォルダー内に隔離し、本番のDLL・INIには適用していない。

## 結論

初回の約9秒の大部分は、BDAの `ITuner::put_TuneRequest` 1回が戻るまでの
**約8.59～8.62秒**だった。予備選局と二度選局は全試行で実行されていない。
予備選局の重複が遅延の原因という仮説は、今回の構成では該当しなかった。

## 条件

- x64 Release_Static、直接I2C制御のTBS6812.dllを使用。
- Tuner/Captureを番号で固定した試験用INI、DebugLog=1。
- チャンネルは初回B070（BS07/TS0）、以降B0B0（BS11/TS0）、B0E0（BS14/TS0、8K）。各2秒収録。
- 毎回別プロセスでOpenTuner→3回の選局→CloseTuner→Release→FreeLibraryを実行。
- BonDriver_BDA内の各呼び出しをsteady_clockで計測。外側のSetChannel時間と最初のデータ到着は既存プローブで計測。
- OS再起動直後・カード電源投入直後の測定ではない。dantto4kの復号・TS変換やTVTest描画時間も含めない。

## 通常設定：各3回の平均

| 処理 | Tuner 0 | Tuner 1 |
|---|---:|---:|
| 選局準備（トーン変更時の既定100ms待機等を含む） | 140.001ms | 105.358ms |
| TSID設定 | 0.025ms程度 | 0.024ms程度 |
| BDAの本選局呼び出し | 8611.464ms | 8595.043ms |
| 本選局呼び出し後のロック確認・待ち | 0.410ms程度 | 0.396ms程度 |
| 初回SetChannel全体 | 8860.060ms | 8808.580ms |
| SetChannel開始から最初のデータまで | 8969.870ms | 8917.363ms |
| 同じオープン中の次の4K選局 | 1027.340ms | 1022.200ms |
| 続く8K選局 | 687.454ms | 692.675ms |

本選局呼び出しの実測範囲は、Tuner 0で8602.259～8620.168ms、
Tuner 1で8591.380～8600.343ms。呼び出しが戻った時点でロック済みだった。
初回SetChannelには、さらに既存の選局後100ms待機、PostLockChannelなどの処理が入る。

## ToneSignalWait=0との比較

試験用INIだけで[Tuner]のToneSignalWaitを100（既定）から0へ変更し、各1回追加測定した。

| 処理 | Tuner 0 | Tuner 1 |
|---|---:|---:|
| 選局準備 | 33.137ms | 0.476ms |
| BDAの本選局呼び出し | 8609.174ms | 8602.616ms |
| 初回SetChannel全体 | 8752.000ms | 8710.100ms |
| 通常設定の平均との差 | 約108ms短縮 | 約98ms短縮 |

トーン待機をなくしても、重いBDA呼び出しの時間はほぼ変わらなかった。
予備選局は通常設定でも省略されており、待機設定だけで数秒短縮する効果は確認できなかった。
この比較は各1回であり、長期安定性や本番設定への採用を判断したものではない。

## 受信・終了の確認

初回選局の8キャプチャ（通常6回＋待機0の2回）はすべてB070で、同期エラー・
MMTP連番欠落・解析不能が0。全8プロセスで受信・通常終了に成功した。

後続の4K/8K選局でも要求したTSIDを確認したが、一部キャプチャには連番飛びが1～3件あった。
選局直後の旧データ混在・連続性は既存の残課題として継続し、この計測で改善済みとは扱わない。

## 次の調査

大幅短縮には、初期化済みの状態を安全に再利用して初回のBDA呼び出しを省けるか、
または初期化・選局経路を直接制御で置き換えられるかの調査が必要。
今回分かったのはCOM/BDA呼び出しの境界までで、呼び出し内部の8.6秒の内訳は未解明。
ハードウェアのロックそのものに8.6秒が必須だとは断定しない。
共有クロック、相手チューナー、通常終了時の復元との両立を確認してから実装を判断する。
